# 05 测试计划

## 1. 思路：先写测试，再写实现

每个接口的验收标准已经写成**契约测试**。每个契约测试都会跑两遍：

| 参数 | 被测对象 | 应该是 |
|---|---|---|
| `[reference]` | 参考实现 `campus_eats/testing/reference.py` | **永远全绿**。变红说明测试或参考实现写错了 |
| `[real]` | 你的正式实现 | 开始时“未实现”，写完一个方法就绿一批 |

测试结束会打印进度表：

```
==================== 各负责人进度（real = 你的正式实现；reference = 参考实现，应全绿） ====================
负责人                  对象         通过  未实现  失败  跳过  合计
A 产品/UI               real           10       0     0     0    10  √ 完成
B 技术负责人            reference      20       0     0     0    20  √ 完成
B 技术负责人（集成）    reference       1       0     0     0     1  √ 完成
C 后端                  reference      29       0     0     0    29  √ 完成
E 测试/运维             reference      17       0     0     0    17  √ 完成
```

- **未实现**：测试撞上了 `NotImplementedError`，代码还没写；
- **失败**：写了，但行为不符合约定，这才需要修；
- **跳过**：如与当前实现无关的测试。

## 2. 怎么跑

```bash
pip install -r requirements-dev.txt

pytest                                       # 全部，看进度表
pytest -k reference                          # 只跑参考实现（提交前必须全绿）
pytest -k real                               # 只跑正式实现
pytest tests/contract/test_decision.py       # 只看一个模块
pytest tests/contract/test_vote.py -k "real and tie"   # 只跑一组
pytest -x --tb=long -k real                  # 遇到第一个失败就停，打印完整报错
pytest tests/api/test_api.py                 # HTTP 接口
```

测试不碰你的 `data/campus_eats.db`：每个测试用临时目录里的新数据库和 `FakeClock`。

## 3. 测试分层

| 层 | 位置 | 内容 | 负责人 |
|---|---|---|---|
| 契约测试 | `tests/contract/` | 每个服务的行为约定；reference / real 各跑一遍 | 各模块负责人 |
| 接口测试 | `tests/api/` | URL、请求 / 响应 JSON、错误映射；后端用参考实现 | A |
| 集成测试 | `tests/integration/` | 抽签 → 评价 → 投票 → 看板；`[real]` 为全部正式实现 | B |
| 界面验收 | 本文 §5 | 手工按清单点一遍，留截图 | A / D，全组参与 |
| 数据验收 | 本文 §6 | 调研 CSV 能导入、字段正确、来源标注 | E / 调研同学 |

## 7. 缺陷跟踪

- 用 GitHub Issues（或组长维护的在线表格）记录：标题、复现步骤、期望 / 实际、截图、环境、负责人、优先级。
- 优先级：P0（演示主流程不可用，当天修）、P1（功能错误，本周修）、P2（体验 / 文案，答辩前修）。
- 修 bug 时先补一条能复现的测试（能用契约测试就用契约测试），再改代码；修完把测试保留。
- 每周例会检查：未关闭 Issue、`pytest` 进度表、里程碑风险。
