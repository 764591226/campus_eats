# 03 详细设计

> 代码里的文档字符串是权威版本；本文解释“为什么这样设计”，并把分散在各文件的规则放在一起看。
> 接口签名见 04 号文档；任何规则改动都要同步改契约测试。

## 1. 通用约定（C 负责解释）

| 项 | 约定 |
|---|---|
| 金额 | 整数“分”，字段名以 `_fen` 结尾；前端显示时除以 100，不上浮存价格 |
| 时间 | epoch 毫秒整数；业务代码只通过 `Clock.now_ms()` 取时间，测试用 `FakeClock` 快进 |
| ID | 稳定的英文 ID（`nh_main`、`tomato_egg`），不用中文名做主键 |
| 枚举 | `str` 枚举，value 即 JSON / 数据库字符串 |
| 实体 | `@dataclass(frozen=True)` 不可变；修改用 `dataclasses.replace` |
| 集合字段 | 实体里用 tuple（tags、open_periods、options），JSON 里是数组；Repository 读回必须还原成 tuple |
| 错误 | 只抛 `CampusError(code, message, **details)`；message 是给最终用户看的中文 |
| 时区 | 评价“自然日”与统计“按日期”固定北京时间（`seed.TZ_OFFSET_HOURS = 8`） |

### 1.1 数据归属与读写权限

每类数据只有一个写入方，其他人只读；所有写入都经过 Repository。

| 数据 | 唯一写入方 | 写入途径 | 读取方 |
|---|---|---|---|
| 校区 / 就餐点 / 菜品 | C（初始化 + 管理后台接口） | `Repository.save_*` / `initialize` | B（候选）、A（后台）、D（页面） |
| 评价 | E | `ReviewService.add_review` / `delete_review` → Repository | C（评分汇总）、B（权重）、A（后台） |
| 决策历史 | B | `DecisionService.decide` → Repository | C（统计）、D（历史列表） |
| 投票房间 / 选票 | B | `VoteService` → Repository | C（统计）、D（投票页） |

禁止事项：B 不直接改菜品；E 不改决策；A / D / 前端不写任何业务数据，只调接口；任何模块不绕过 Repository 读写数据库。

## 2. 数据模型

### 2.1 实体关系

```
Campus 1 ── * Venue 1 ── * Dish 1 ── * Review
                                  │
                                  ├── * Decision（历史快照，只引用 ID）
                                  └── * VoteOption（投票选项是快照标签，不强制外键）

VoteRoom 1 ── * VoteBallot（(room_code, voter_token) 唯一）
```

### 2.2 表结构（`campus_eats/model/schema.sql`）

| 表 | 主键 | 说明 |
|---|---|---|
| campuses | id | 名称、别名（JSON 数组） |
| venues | id | 校区、名称、类型、位置、营业时段（JSON）、标签（JSON）、是否营业 |
| dishes | id | 地点、菜名、分类、价格（分）、标签（JSON）、描述、是否在售、来源、更新时间 |
| reviews | review_id 自增 | 菜品、1–5 星、评论、昵称、时间 |
| decisions | decision_id | 菜品、地点、模式、时间；用于最近去重、热度与看板 |
| vote_rooms | code | 标题、选项（JSON）、发起人、创建 / 截止时间、状态 |
| vote_ballots | (room_code, voter_token) | 选项、时间；改票即覆盖同一主键 |

嵌套字段存 JSON 而不拆表：查询模式简单（按整体读出后再计算），拆表反而增加 C 的工作量。C 想拆表也可以，只要契约测试通过。

### 2.3 初始数据（`campus_eats/model/seed.py`）

- 校区：马房山 `ms`、南湖 `nh`。
- 就餐点 4 个：东院食堂、西院食堂、南湖食堂、外卖轻食样例（外卖样例包含夜宵时段）。
- 菜品 12 道，覆盖盖饭、面食、小吃、套餐、饮品；其中 `source=DEMO` 的是演示占位，`source=TAKEOUT` 的是外卖手工样例。
- 演示评价 5 条（匿名昵称），让首页一打开就有评分可看。
- 所有演示菜名、窗口名**不代表真实调研结果**，答辩前用 07 号文档的流程替换。

## 3. 筛选管线（B）

`DecisionService.candidates(filters)` 按以下顺序过滤，任何一步失败都提前返回空（最终抛 `NO_CANDIDATE`）：

1. **地点**：按 `campus_id`、`kinds`、`meal_period` 调 `CatalogService.list_venues`；只保留 `available=True`；如果指定了 `venue_ids`，再与地点集合求交。
2. **菜品**：`list_dishes(venue_id)` 默认只返回 `available=True`；应用 `exclude_dish_ids`、`max_price_fen`、`categories`、`include_tags`（必须全部包含）、`exclude_tags`（包含任一就排除）。
3. **最近吃过**：计算 `since = now - recent_days × 24h`，取该时间后的 `decisions.dish_id` 集合；给候选打 `recent` 标记。
4. **去重策略**：`exclude_recent=True` 时优先只返回 `recent=False` 的候选；若一个都不剩（全都吃过），返回全部候选，由 `decide()` 兜底并在理由中说明。`exclude_recent=False` 时不过滤，只保留 `recent` 标记给界面。
5. 候选按 `dish.id` 排序，保证同一随机种子下结果可复现。

完全没有候选（不是“都被最近排除”，而是筛选条件本身匹配不到）→ `NO_CANDIDATE`，message 提示“放宽一个筛选条件”。

## 4. 加权抽签（B）

### 4.1 权重

```
weight = 20 + round(评分平均分 × 10) + min(近 30 天被抽中次数, 30)
```

- 评分 1–5 → 10–50；无评分按 0 算（权重 20）。
- 近 30 天热度最高加 30；这样“常被抽中”的菜更容易被抽中，但不会碾压高评分。
- 权重范围 20–100，全部为整数，避免浮点抖动。

### 4.2 抽取与备选

1. 用 `random.Random` 的 `choices(population, weights, k=1)` 抽第一名；
2. 从剩余候选里按同样权重再抽，最多 2 个备选，不重复；
3. 生产环境使用系统随机源；测试通过 `wiring.build(..., rng=random.Random(1234))` 固定种子。

### 4.3 结果与历史

```
Decision(decision_id, dish_id, venue_id, mode, created_at)
decision_id = "D{created_at}-{4 位十六进制随机}"
```

- `mode` 只影响展示（转盘 / 抽签），两种模式算法相同。
- 每次 `decide` 立即写 `decisions`，用于热度、最近去重和历史；历史只存 ID，界面展示时再查菜品快照。
- `reason` 形如：`最近都吃过了，这次从全部候选里抽 · 评分 4.6（12 条评价） · 近 30 天被抽中 5 次`；没有评价 / 热度的部分用“暂无评分”“还没有被抽中过”。

### 4.4 “再抽一次”

前端把当前结果的 `dish.id` 放进 `exclude_dish_ids` 再请求。被排除的菜在本次会话内不再出现；点“清空排除”后恢复。若排除后没有候选，接口返回 `NO_CANDIDATE`，前端提示放宽条件。

## 5. 投票（B）

### 5.1 状态机

```
        create_room                close_room / now >= closes_at
OPEN ───────────────► OPEN ─────────────────────────────► CLOSED
   （创建即 OPEN）          cast_vote（可多次，改票覆盖）
```

- 截止判断发生在每次读 / 写房间时（`get_room` / `cast_vote` / `close_room`），不依赖后台线程或浏览器计时。因此“没人看的时候”房间状态可能暂时还是 OPEN，下次访问会自动关闭。
- 已关闭的房间不能再投票；重复关闭 → `INVALID_STATE`。

### 5.2 分享码

- 长度 6，字符集 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（去掉 I、O、0、1，避免念错）。
- 生成后检查 Repository 是否已存在，冲突就重抽；`code` 是全局唯一主键。

### 5.3 选项与票数

- 选项是**快照**：`VoteOption(option_id, label)` 在创建时写入房间。这样投票页不依赖菜品 / 食堂是否被删除，分享链接长期有效。
- `option_id` 不重复，2–8 个；`label` 1–30 字。
- 每个 `voter_token` 在房间内最多一条选票；再次投票覆盖旧选择（改票），总票数不变。
- 结果：
  - 所有选项按房间创建时的顺序返回，票数为 0 的也返回；
  - `winners` 是票数最高的选项；若最高票由多个选项共享且总票数 > 0，则 `tie=True`，`winners` 包含全部并列项；
  - 0 票时 `winners=()`、`tie=False`。

### 5.4 参数校验

| 项 | 规则 |
|---|---|
| 标题 | 去掉首尾空格后 1–40 字 |
| 选项 | 2–8 个，ID 不重复，名称非空 |
| 时长 | 60 000 ms – 7×24×60×60 000 ms |
| 发起人 / 操作人 | 1–20 字 |
| voter_token | 8–64 字符 |
| 选项 ID | 必须属于该房间 |

## 6. 评价（E）

- **评分**：整数 1–5；`True/False` 和 `"5"` 都判非法。
- **昵称**：去掉首尾空格后 1–20 字；不做账号。
- **评论**：可空，去掉首尾空格后 ≤200 字。
- **限流**：同一 `author` + 同一 `dish_id`，同一**北京时间自然日**最多一条；跨天（`FakeClock` 前进 24h）即可再评。返回 `RATE_LIMITED`（HTTP 429）。
- **汇总**：`average = round(sum(rating)/count, 1)`，无评价为 `0.0`；`histogram` 固定包含 1–5 五个键，没有的为 0。
- **列表**：按 `created_at` 降序，时间相同按 `review_id` 降序；`limit` 1–100。
- **删除**：管理员填操作人后删除，返回被删记录；不存在 → `NOT_FOUND`。

## 7. 数据管理与后台（C / A）

- **查询**：默认只返回 `available=True` 的菜品与地点；`include_unavailable=True` 仅管理后台使用。关键词匹配菜名、描述、标签，忽略大小写。
- **新增 / 修改**：按稳定 ID 覆盖（幂等）。校验 id / name 非空、地点存在、分类合法、价格 0–100000 分（0–1000 元）、`open_periods` 非空。保存时 `updated_at = clock.now_ms()`。
- **上下架**：只改 `available`，不做物理删除；抽签、公开列表、详情之外的入口都会隐藏它，但历史决策和评价保留。
- **权限**：没有账号，只有“操作人昵称”非空校验；演示环境默认信任。公网部署不在本项目范围。
- **数据来源**：`Dish.source` 区分 `DEMO` / `SURVEY` / `TAKEOUT`；界面必须显示来源，避免把演示数据说成调研结果。

## 8. 统计（C）

`StatsService.summary(campus_id, since_ms, until_ms)`：

- 默认 `since=0`、`until=now+1ms`（保证刚刚发生的操作计入）；显式传入时 `until` 不含。`since > until` → `INVALID_FILTER`。
- `decision_count`：区间内、且菜品所在校区匹配的决策数。
- `by_campus`：`{campus_id: 决策数}`；`by_category`：`{分类枚举值: 决策数}`。
- `top_dishes`：按菜品 ID 计数，label 形如 `番茄炒蛋盖饭 · 东院食堂`；次数降序，同次数按 label 升序，最多 5 个。
- 评价：区间内的评价；按校区过滤时通过菜 → 地点 → 校区判断；`avg_rating` 1 位小数，`review_count` 条数。
- 投票：区间内创建的房间数；这些房间内、区间内创建的选票数。
- `popular_dishes(limit, campus_id)`：全时间的热门菜，规则同上，最多 50。

## 9. 错误码

| ErrorCode | HTTP | 什么时候用 | 前端怎么处理 |
|---|---|---|---|
| INVALID_ARGUMENT | 400 | 字段缺失、类型不对、评分越界、价格越界 | 指出具体字段 |
| INVALID_FILTER | 400 | 校区不存在、开始时间晚于结束时间 | 提示并恢复默认筛选 |
| NOT_FOUND | 404 | 菜品 / 地点 / 评价 / 投票不存在 | 提示并回到入口 |
| NO_CANDIDATE | 409 | 筛选后没有可抽的菜 | 建议放宽条件 / 清空排除 |
| INVALID_STATE | 409 | 投票已结束、重复结束 | 刷新投票状态 |
| RATE_LIMITED | 429 | 同一天重复评价同一道菜 | 提示明天再来 |

## 10. 已知局限

- 无账号体系，管理后台与投票 token 都依赖“演示环境可信”；公网部署需另加鉴权。
- 投票 token 存在浏览器 localStorage，清缓存可以再投一票；不追求严格防刷。
- 抽签权重是启发式；样本少时评分波动大，可能造成某些菜被频繁抽中。
- “最近吃过”只记录本机数据库里的抽签结果，不区分不同用户。
- 菜品数据依赖线下调研，过期不会自动更新；页面只标注来源与更新时间。
- SQLite 单机单进程；多人同时大量写入不是本项目目标。
- 参考实现的数据在内存中，重启即清空；只有 `--real repository` 才持久化。
