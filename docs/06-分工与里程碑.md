# 06 分工与里程碑

> 依据：课程第一讲“小型软件项目团队成员结构”给了 6 个角色；我们只有 5 个人，把 **UI 设计师 & 文档管理工程师** 合并进 **项目 / 产品负责人**（这两个角色本来就是一个人的组合，且都要产出文档与界面规范）。其余 5 个角色一人一个。
> 课程注明：**全体成员都要承担开发任务**。所以每个角色都有明确的代码和测试产出，不存在只写文档或只测不写的人。
> 仓库与文档只使用 **A–E 代号**，不记录姓名；代号按角色建议分配，第一次会议确认后可互换，角色职责不变。

## 2. 每个人做什么

### A · 项目 / 产品负责人 + UI & 文档

**课程职责**：确保项目按需求、按时交付；需求管理、进度把控、沟通协调、交付验收（对应“项目/产品负责人”）；设计美观界面、整理全流程文档、归档到共享平台（对应“UI 设计师 & 文档管理工程师”）。

**本项目必做**

1. **需求与进度**：维护 01 号文档的需求编号与变更；每周更新进度表（谁、哪条需求、状态、风险）；组织活动 1–6 的会议并留记录。
2. **UI 规范**：输出配色、字号、间距、圆角、按钮 / 表单 / 错误 / 空状态规范；三个页面（抽签 / 投票 / 后台）的线框与关键状态图。已有 `css/theme.css` 作为起点，负责定稿。
3. **HTTP 接口层**：维护 `web/api.py`，保证 URL / JSON / 错误码符合 04 号文档；`tests/api/test_api.py` 全绿。
4. **管理后台前端**：菜品 / 窗口列表、新增与修改、上下架、评价管理、看板（A-04），与 C 的接口联调。
5. **文档与验收**：01–07 的收集归档；会议记录、调研照片索引、演示截图；组织 05 §5 手工验收并记录问题。
6. **演示**：按 01 §6 写演示脚本、准备讲稿，活动 6 主讲或分工讲。

**自由发挥**：深色模式、动效节奏、键盘操作、读屏标签、打印 / 海报样式。
**边界**：不在 `api.py` 写业务规则；不改 B/C/E 的服务实现；界面数据一律通过 `js/api.js`。
**交付物**：定稿设计规范、可用的后台页面、API 测试全绿、会议与验收记录、演示脚本。

### B · 技术负责人（兼后端开发）

**课程职责**：确定技术方案、架构与代码规范，解决技术难题，保证开发顺畅与代码质量，兼任后端工程师，做代码审查与配置审查。

**本项目必做**

1. **技术与架构**：确认 02 号文档的技术选型、分层与依赖规则；和 C 在活动 3 前**冻结**实体、接口与错误码；维护 04 号文档。
2. **决策服务**：`DecisionService` 的筛选管线、权重、兜底、备选、历史（DEC-01～05），代码在 `decision/decision_service.py`；`test_decision.py` 的 real 全绿。
3. **投票服务**：`VoteService` 的房间、分享码、改票、截止、平票（VOTE-01～04）；`test_vote.py` 的 real 全绿。
4. **组装与集成**：维护 `wiring.py`；保证 `--real <组件>` 可以逐个替换；`test_flow.py` 在 `--real all` 下全绿。
5. **代码审查**：每人合并前至少看一遍其核心逻辑；重点检查“业务规则是否漏到 web / 前端”“是否绕过 Repository”。
6. **技术难题**：跨模块联调、性能 / 响应异常、部署时的技术问题；每周例会上给出结论。

**自由发挥**：权重公式可配置、投票防刷频率限制、多轮投票、结果导出。
**边界**：只通过 `CatalogService` 和 `Repository` 取数据；不替 C 写 SQL；不单方面改实体字段（走 04 §4 流程）。
**交付物**：决策 / 投票实现与测试、接口契约定稿、集成测试全绿、代码审查记录。

### C · 后端开发工程师

**课程职责**：实现后台逻辑、数据存储与接口服务，保证稳定与数据安全；数据设计、接口开发、逻辑实现、数据交互、联调与修复。

**本项目必做**

1. **数据结构**：和全组过一遍 `entities.py`、`enums.py`、`errors.py`、`seed.py`；第一周内冻结，之后改动走接口流程。
2. **SQLite Repository**：`schema.sql` 建表；`SqliteRepository` 实现全部方法；嵌套字段 JSON 化后读回要还原成 tuple / 枚举；初始化幂等；Flask 多线程下写操作加锁；重启数据不丢（DAT-02）。
3. **数据管理**：`CatalogService` 的查询、关键词、增改、上下架、详情（CAT-01～04）；`test_catalog.py` real 全绿。
4. **统计**：`StatsService` 的看板与热门菜（STA-01～02）；`test_stats.py` real 全绿。
5. **数据支撑**：配合 E 的导入工具调整 Repository；准备 3 校区演示数据与来源标记；性能上给常用查询加索引。
6. **联调**：响应 B 的筛选需求、A 的后台需求、E 的导入需求。

**自由发挥**：拆表 / 索引策略、数据库备份、CSV 导出、初始化数据校验。
**边界**：Repository 只存取、不做业务判断；业务服务不写 SQL；不改前端展示逻辑。
**交付物**：SQLite Repository 与全部后端查询、三组契约测试 real 全绿、演示数据与导入支持。

### D · 前端开发工程师

**课程职责**：实现用户可见的界面与交互，保证页面美观、操作流畅、适配不同设备；页面开发、交互实现（包括错误提示）、接口对接（包括异常）、适配与优化（包括加载速度）。

**本项目必做**

1. **抽签首页**：筛选面板、结果卡片、再抽一次、排除提示、最近历史（FE-01～04）；遵守 A 的 UI 规范。
2. **转盘 / 抽签动效**：转动、停下的节奏；结果出现时机；不阻塞请求；尊重 `prefers-reduced-motion`（加分）。
3. **评价交互**：星级选择、昵称、评论、提交成功 / 429 提示、评分即时刷新（FE-03）。
4. **投票页**：选项、计票条、改票、3 秒轮询、截止 / 平票展示（FE-05）。
5. **接口对接**：所有请求走 `js/api.js`；统一处理 400 / 404 / 409 / 429 / 网络错误；不把业务规则写在前端（FE-06）。
6. **响应式**：360px、768px、桌面三档自测；无横向滚动；触控目标 ≥44px（FE-07）。
7. **协作**：与 A 对齐设计 token；与 B 对齐 JSON 字段；与 E 一起走界面验收。

**自由发挥**：骨架屏、结果海报导出、分享文案、微动效、PWA。
**边界**：不在前端算价格 / 权重 / 是否可抽；不直接拼 HTML 插入用户输入；不改后端接口。
**交付物**：三个页面可完整演示、错误状态齐全、移动端截图、界面验收记录。

### E · 测试 / 运维工程师（兼评价开发）

**课程职责**：提前发现 bug，确保上线稳定；制定测试计划与用例、执行测试、记录 bug 并跟进修复；部署测试 / 开发环境、部署软件、执行维护。

**本项目必做**

1. **评价服务**：`ReviewService` 全部方法（REV-01～03），`test_review.py` real 全绿；重点同日限流与评分汇总。
2. **测试计划**：维护 05 号文档；按需求编号维护用例；组织全组手工验收并留证据。
3. **测试资产**：维护 `tests/contract/`、`tests/api/`、`tests/integration/` 与进度看板；保证 `pytest -k reference` 始终全绿；不为了让测试变绿而放宽断言。
4. **缺陷跟踪**：GitHub Issues / 表格；P0/P1/P2 分级；每周例会检查未关闭项；修复后补回归测试。
5. **运维**：`requirements*.txt`、虚拟环境说明、`start.bat`、`run.py --lan` 的局域网演示；数据库备份与恢复；演示前从空库彩排。
6. **数据导入**：维护 `surveys/survey-template.csv` 与 `tools/import_survey.py`；导入前 dry-run，导入后核对来源、价格、窗口。
7. **发布检查**：按 05 §8 的清单逐项签字。

**自由发挥**：GitHub Actions 自动测试、日志、简单监控、覆盖率报告。
**边界**：不修改别人负责的产品代码（发现问题提 Issue 或和负责人一起改）；测试不得绕过接口直接改数据库。
**交付物**：评价模块、测试计划与用例、缺陷清单、可复现的演示环境、导入工具与数据核对记录。

## 3. 依赖与并行

```
第 1 周   C 冻结数据结构 ──┐
          B 冻结接口契约 ───┼──► 之后所有人并行
                            │
          A 用参考实现做后台 / 接口      （不依赖 C）
          D 用参考实现做页面            （不依赖任何人）
          B 用参考 Catalog 写决策投票   （不依赖 C 的 SQLite）
          C 写 SqliteRepository        （不依赖 B）
          E 写评价 + 测试              （不依赖任何人）
```

因为有参考实现，**没有人需要等别人写完**。每个人随时可以：

```
python run.py --real decision       # B 看自己的决策 / 投票
python run.py --real catalog,stats  # C 看自己的查询与统计
python run.py --real reviews        # E 看评价
python run.py --real all            # 最终演示
pytest -k real                      # 看自己还剩多少“未实现”
```

## 5. 协作规则

- **分支**：每人一个长期分支：`feat/web-a`、`feat/decision-b`、`feat/data-c`、`feat/frontend-d`、`feat/qa-e`。合并到 `main` 走 Pull Request，至少 1 人 review（B 看代码，A 看文档与界面）。
- **提交前**：`pytest -k reference` 必须全绿；提交说明写清楚“改了什么、影响谁、对应需求编号”。建议使用 `feat:` / `fix:` / `docs:` / `test:` 前缀。
- **接口变更**：走 04 §4 流程；不要在自己的分支里悄悄改 `interfaces.py` 或 JSON 字段。
- **AI 代码**：可以用 AI 生成实现或测试，但提交前必须自己读一遍、能解释每段在干什么（课程要求）；参考实现也是 AI 参与写的，同样适用。禁止用 AI 生成“放宽断言”的测试。
- **数据库文件**：`data/`、`*.db` 在 `.gitignore` 里，不提交；演示前备份到共享盘。
- **调研数据**：仓库只放模板与脱敏后的 CSV；原始照片、含个人信息的访谈记录放共享盘，不进 git。
- **会议**：每周一次 30 分钟站会：上周完成 / 本周计划 / 阻塞 / 风险；A 记录，E 更新缺陷清单。
- **验收**：每次合并后由 A 或 E 跑一遍对应页面的手工清单，留截图。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 线下调研拖延 | 数据不真实、答辩被问 | W1 定人定校区；W2 先交 1 个校区；演示数据明确标注 DEMO；调研未完成不谎称真实 |
| “太简单”被扣分 | 分数 | 用调研 + 评分闭环 + 群体投票 + 数据看板 + 测试与文档证明工作量；不再堆无意义功能 |
| 5 人工作量不均 | 有人空闲 / 有人爆肝 | 按 §1 工时与代码边界执行；每周看进度表调整；B/A 可临时补位 |
| 集成拖到最后 | 演示失败 | 参考实现让所有人随时可跑；W3 起每周 `--real all`；W4 冻结功能只修 bug |
| 成员临时缺席 | 进度 | 结对时互相讲代码；关键模块（Repository / 决策 / 前端首页）各有备份人 |
| 局域网 / 防火墙演示失败 | 投票演示受阻 | W3 就测 `--lan`；准备两台设备 + 热点；失败时用同一浏览器多标签演示改票 |
| 需求膨胀 | 延期 | MVP = 01 必做；加分项进 backlog，W4 后不再加功能 |
| AI 代码看不懂 | 答辩被问倒 | 每段 AI 代码提交前由作者注释、讲给结对伙伴；测试能证明行为 |
| 数据隐私 / 合规 | 风险 | 不收集个人信息；不爬外卖平台；照片征得同意；投票 token 匿名 |
