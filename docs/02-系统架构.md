# 02 系统架构

## 1. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 界面 | HTML / CSS / 原生 JS（无构建工具） | 小微项目，开箱即用；手机浏览器直接打开投票页 |
| 后端 | Python 3.10+，Flask | 组员熟悉 Python；只负责 HTTP，足够轻 |
| 数据库 | SQLite（标准库 sqlite3） | 单文件，不装数据库服务；拷走 `data/*.db` 就能演示 |
| 数据访问 | Repository 模式 | 业务代码不写 SQL；参考实现和正式实现可以互换 |
| 测试 | pytest | 契约测试 + 进度看板；用 FakeClock 让时间可控 |
| 部署 | 本机进程 / 局域网 | `python run.py` 一条命令；`--lan` 让手机打开投票链接 |

运行依赖只有 `flask`；开发另需 `pytest`。不需要 Node、数据库服务或外网。

## 2. 总体结构

```
┌────────────────────── 浏览器（电脑 / 手机）──────────────────────┐
│  抽签页 index.html        投票页 vote.html        后台 admin.html  │  ← D / A
│  共同：js/api.js（请求封装） · css/theme.css（设计规范）            │
└──────────────────────────────┬───────────────────────────────────┘
                               │ HTTP / JSON（04 号文档 §3）
┌──────────────────── Python 进程（python run.py）──────────────────┐
│  web/api.py        HTTP 接口层：解析请求 → 调服务 → 转 JSON     ← A │
│ ───────────────────────────────────────────────────────────────── │
│  decision/         DecisionService · VoteService                 ← B │
│  review/           ReviewService                                 ← E │
│  catalog/          CatalogService · StatsService                 ← C │
│ ───────────────────────────────────────────────────────────────── │
│  model/            实体 · 枚举 · 错误 · Repository · 初始数据     ← C │
│  wiring.py         组装：每个组件选正式实现或参考实现             ← B │
└──────────────────────────────┬───────────────────────────────────┘
                               │
                     data/campus_eats.db（SQLite）
```

## 3. 模块依赖

```
web.api ──► decision.DecisionService ──► catalog.CatalogService ──► review.ReviewService
   │             │                              │                          │
   │             └──► vote.VoteService          └──► Repository ◄──────────┘
   │                                                   ▲
   └──► stats.StatsService ────────────────────────────┘
```

规则（违反任何一条都算 bug）：

1. **只依赖接口，不依赖实现**。构造函数参数类型都是 `interfaces.py` 中的抽象类，具体实现由 `wiring.py` 决定。
2. **只有 Repository 能碰数据库**。其他模块不写 SQL；管理后台与工具也一样。
3. **下层不知道上层**。`model` 不导入任何业务模块；`catalog` 不导入 `decision`；没有模块导入 `web`。
4. **业务规则不写在 HTTP 层和前端**。能否抽、权重、投票截止、评价限流都由后端决定；前端只展示。
5. **统一错误**：任何模块只抛 `CampusError(code, message, details)`，web 层统一映射成 HTTP 状态码。
6. **时间统一从 Clock 取**。测试用 `FakeClock.advance()` 复现“到点自动截止”“第二天才能再评价”。

## 4. 关键机制

### 4.1 参考实现 + 正式实现

每个接口都有两套实现：

| | 参考实现 `campus_eats/testing/reference.py` | 正式实现（各人的文件） |
|---|---|---|
| 谁写 | 仓库已提供 | 各负责人 |
| 数据 | 内存，重启即清空 | SQLite，重启不丢 |
| 用途 | 证明契约测试正确；别人没写完时顶上，让完整程序先跑；接口疑问的参考 | 最终交付 |

启动时可以逐个替换：

```
python run.py                          # 全部参考实现
python run.py --real catalog,stats     # 只有 C 的几个组件用正式实现
python run.py --real all               # 最终演示
```

因此**没有人需要等别人写完**：A / D 用参考实现就能开发页面，B 用参考 Catalog 就能写决策，C 可以单独测 Repository。

### 4.2 抽签是同步计算，投票用轮询

- 抽签：一次 `POST /api/decisions` 同步完成筛选、加权随机、写历史并返回结果；前端只负责动画。
- 投票：页面每 3 秒 `GET /api/votes/<code>` 拉一次结果；截止时间在服务端判断（按 Clock），不依赖浏览器计时。没有后台线程，测试可确定性复现。

### 4.3 每次操作都留下痕迹

- 抽签写 `decisions`，用于“最近 7 天去重”、热度权重和看板；
- 评价写 `reviews`，评分参与权重；
- 投票写 `vote_rooms` / `vote_ballots`，用于实时计票和参与统计；
- 菜品上下架只改 `available`，历史决策与评价不删。

## 6. 运行与部署

```
python -m venv .venv
.venv\Scripts\activate            # Windows
pip install -r requirements-dev.txt

python run.py                     # http://127.0.0.1:3200
python run.py --open              # 自动打开 Edge 应用窗口
python run.py --lan               # 手机同 Wi-Fi 可打开投票链接
python run.py --real all          # 最终演示（全部正式实现）
pytest                            # 契约测试 + 进度表
```

局域网演示时，Windows 第一次可能弹出防火墙提示，选择“允许专用网络”。手机打不开时先确认电脑和手机在同一 Wi-Fi，再用 `run.py` 打印的 IP 尝试。
