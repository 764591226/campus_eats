# 01 需求规格

> 依据：课程《软件工程》第一讲“团队开发模式”中的小型软件项目团队结构（项目 / 产品负责人、技术负责人、后端、前端、测试 / 运维、UI 与文档），以及小组在群里确定的方向：**“今天吃什么 / 校园决策助手”**。
> 状态：**草案 v0.1（2026-11-14），待全组确认**。需求先改这里，再改接口与测试；每条需求都有编号，05 号文档按编号对应测试。
> 规模约束：小微项目、MVP、1–3 个月、无复杂架构；用主流技术即可，不做登录、支付和真实外卖对接。

## 1. 项目定位

一个面向本校学生的**吃饭决策助手**。用户不用注册，打开网页选几个条件（校区、时段、预算、口味），点一下转盘 / 抽签，系统从**食堂窗口和外卖样例**里加权随机抽一道菜；抽中后可以看评分、写评价，也可以发起一个投票，把“聚餐去哪”交给全组同学决定。

和“纯随机转盘”的区别，也是本项目的“认真程度”所在：

1. **真实的调研数据**：马房山、南湖两个校区分别线下跑窗口，把价格、位置、营业时段、菜品标签录进数据库（07 号文档）。
2. **可解释的随机**：按评分和近 30 天热度加权，自动跳过最近 7 天吃过的菜、歇业窗口和用户排除的菜（03 号文档 §5）。
3. **群体决策**：6 位分享码的投票房间，一人一票、可改票、自动截止、平票提示（03 号文档 §6）。
4. **评价闭环**：评分与评论会反过来影响抽签权重；管理后台可以维护菜品、上下架、看数据（03 号文档 §7–§8）。

### 1.1 与原题的扩展关系

原题（subject.png）是“输入选项 → 转盘 / 抽签”的极简工具，“纯前端 + 简单后端，1 周即可写完”。为了让它撑起 5 个人的工作量、又符合课件“小微项目”的边界，我们做了**有节制的扩展**，不是堆功能：

| 原题 | 本项目的扩展 | 为什么值得做 |
|---|---|---|
| 输入几个选项，随机决定 | 两校区真实窗口 + 外卖样例；按预算 / 时段 / 口味筛选；加权随机、最近去重、备选、历史 | 数据来自调研，不是编的；算法可解释，老师能现场验证 |
| 转盘 / 抽签 | 保留转盘和抽签两种模式 | 主题不变，视觉与交互仍是核心 |
| 投票决定聚餐地点 | 6 位分享码、匿名一人一票、可改票、自动截止、平票 | 真正的多人场景，正好覆盖后端状态机与手机端联调 |
| — | 评分 / 评论闭环 | 让“抽签”不是一次性玩具；评分反过来影响权重 |
| — | 管理后台 + 数据看板 | 对应课程的后端、数据维护与统计能力；答辩有数据可看 |
| — | 契约测试、参考实现、CI 式进度表、调研与部署文档 | 对应团队角色与软件工程流程，体现“工程”而不只是“能跑” |

同时保持小微项目约束：不做登录、支付、真实下单、复杂架构和机器学习；技术栈就是 Flask + SQLite + 原生前端。

| 课程中的角色 | 本项目里的含义 | 负责人 |
|---|---|---|
| 项目 / 产品负责人 | 需求与进度、UI 规范、文档归档、管理后台前端、HTTP 接口层 | A |
| 技术负责人（兼后端开发） | 技术选型、架构、接口契约、代码审查；决策与投票服务 | B |
| 后端开发工程师 | 数据结构、SQLite、地点 / 菜品管理、统计 | C |
| 前端开发工程师 | 抽签主流程、转盘动画、评价、投票页、接口对接与适配 | D |
| 测试 / 运维工程师 | 测试计划与用例、契约 / 接口 / 集成测试、部署与数据导入；评价服务开发 | E |
| UI 设计师 & 文档管理工程师 | 与项目 / 产品负责人合并（5 人组的合并方式，见 06 号文档 §1） | A（兼） |

## 2. 角色与场景

- **学生用户**：不登录，打开首页选条件 → 抽签 → 看结果 → 打分 / 评论；可以重复抽，但同一轮内会排除抽到过的菜。
- **投票发起人**：在首页选 2–8 个候选地点，生成 6 位分享码和链接，发到班级 / 寝室群；在投票页可以手动结束。
- **投票参与者**：同一个浏览器一个匿名 token，一人一票，截止前可以改票；不收集姓名、学号、手机号。
- **维护人员（组员 / 助教）**：打开 `/admin`，维护菜品和窗口、上下架、删除不当评价、查看看板；不做账号体系，用“操作人昵称”记录。

## 4. 非功能需求

| 编号 | 需求 |
|---|---|
| NF-01 | Python 3.10+；`pip install -r requirements.txt` 后 `python run.py` 即可用，不需要数据库服务、Node 或外网 |
| NF-02 | 金额一律整数“分”，前后端都不得用浮点存价格；评分是唯一允许的小数 |
| NF-03 | 用户输入一律用 `textContent` 插入页面，不拼接 HTML，防止 XSS |
| NF-04 | 任何接口错误都返回统一格式；前端不出现未处理的异常或白屏 |
| NF-05 | 单页在 360px 宽度下可用；按钮触控面积不小于 44×44px |
| NF-06 | 不收集姓名、学号、手机号；投票 token 是随机串，不关联身份 |
| NF-07 | 不爬取真实外卖平台；外卖数据只做手工录入样例并标注“外卖样例” |
| NF-08 | 所有 AI 生成代码必须有人读懂再提交；接口与测试必须能讲清楚 |
| NF-09 | 参考实现必须 100% 通过契约测试；正式实现按模块逐个变绿 |

## 5. 假设与不做的事

- 不做真实下单、支付、配送；只做“决定吃什么”，不承担交易。
- 不做账号体系。管理后台不设密码，演示环境由组员/助教使用；若公网部署必须加鉴权（本项目不公网部署）。
- 不爬取外卖平台数据（合规与接口稳定性都不合适）；外卖仅作为“选项来源”手工录入。
- 食堂营业时间、菜品价格以调研当天为准；页面标注“数据更新于调研日”，过期数据不自动刷新。
- 投票结果用轮询（3 秒）而非 WebSocket：小微项目足够，部署简单。
- 同一浏览器的匿名 token 可以被清缓存绕过，投票不追求严格防刷；加分项再做频率限制。
- 抽签权重是启发式，不做机器学习；评分少时权重主要由基础分和热度决定。
- 全部为单机部署；SQLite 单文件，适合课程演示。

## 6. 演示脚本（活动 6 / 答辩用，约 5 分钟）

1. 打开首页，说明两个校区和“演示数据 / 调研数据”的标识；切到“南湖校区 + 午餐 + ¥15 以内 + 不吃辣”。
2. 点“转一下”：转盘动画 → 结果卡片显示菜名、窗口、价格、评分、抽中理由；指出它跳过了最近吃过的菜。
3. 给结果打 5 星、写一句评论并提交；再打开“最近抽过”，说明权重会随评价和热度变化。
4. 点“再抽一次”，展示当前菜被排除；再抽一次仍能抽到符合条件的菜。
5. 在“拉同学投票”里勾选 2–3 个食堂，生成链接；用手机（同一 Wi-Fi，`--lan`）打开投票页，另一台设备投另一项，展示实时计票与“改票”。
6. 手动结束投票，展示获胜 / 平票提示。
7. 打开 `/admin`：新增一道“调研数据”菜、下架一道菜、删除一条评价；回到首页展示下架的菜不再出现。
8. 打开看板：抽签次数、评价数、平均分、投票人次、热门菜 Top 5；说明这些数据来自刚才的操作。
9. 收尾：展示 `pytest` 进度表（参考实现全绿，正式实现按模块完成）和 07 号调研原始照片 / CSV，说明数据真实性。

## 7. 验收标准

- **MVP = 本文所有“必做”**，缺一项不算完成。
- `pytest -k reference` 全绿；`pytest` 进度表中各负责人 `real` 全部“√ 完成”。
- 按 §6 在**空数据库**上完整走一遍，不出现报错、白屏或横向滚动。
- 07 号文档要求的调研数据至少覆盖 2 个校区、每校区 2 个就餐点、每个就餐点 3 道菜，并在页面上可见来源标注。
- 全组能解释自己负责模块的代码、接口和测试；AI 生成的代码同样要能讲清楚。
